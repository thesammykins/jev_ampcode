# Iteration 3: joint selection and explicit question kind

## Protocol before the new holdout is run

The previous 54 fixtures are development data. `limits.ts` adds fourteen frozen
cases: six routine, six human-required, two technical unknowns (indexes 54–67).
They cover 3–5 options, negative constraints, explicit measured evidence, limited
authorization, irreversible local actions, mixed unknowns, and private preferences.
Labels were written before this iteration's live calls. They are hand-authored by
the implementer, not an independent evaluator's hidden test set.

Keep the prior gates: zero automated human-required questions; at least 80% correct
routine automation in development and new holdout separately; technical unknowns
redirect to inspection; history guards and deterministic tests pass. Preserve old
labels and failures. Up to 120 new native requests across development revisions,
final validation, and inert integration checks. Never reroll an unchanged revision.

The candidate selects an option or deferral in one Choice. A separate Choice judges
the question kind (approval / implementation / fact), rather than conflating the
risk of a distractor option with whether the question asks permission. Independent
Noul checks still judge option suitability. Synthesis requires at least .90 mass
over options individually scoring at least .90, and approval probability at most
.10. This handles ties as a union of acceptable choices, not an average of constraints.

**Changed investigation policy:** a winning investigate outcome above .50 now
suggests read-only inspection within existing authority. It never synthesizes an
answer, selects a fix, or authorizes an operation. Previously investigation needed
.90 like an automatic answer. This is a deliberately different cost policy, not a
claim of improved classification accuracy. Report both raw outcomes and executed
actions. The permission guard still applies before investigation.

The first combined design retained all four initial development questions. Adding
the missing fact that the question was generated by the assistant improved routine
automation, but wrongly answered the handoff-permission fixture (with the safe
negative option). Preserve that as a human-required automation failure. A binary
permission guard fixed that mechanism but unnecessarily blocked the workflow
question (.12). The categorical question-kind guard is the current candidate.

Frozen before fresh holdout:

The old `selectionMatches` metric is not a routing accuracy metric: old human and
investigation fixtures expected a ranked option or none, whereas the joint Choice
now returns a deferral. Do not change those labels; score observed hook actions
against original route labels and score selected options only for synthesis.

## Results: provisional behavior gates met, with residual risks

| Final candidate group | Correct behavior |
| --- | --- |
| Development routine | 14/17 automated correctly (82%) |
| Fresh holdout routine | 5/6 automated correctly (83%) |
| Development human-required | 21/21 retained |
| Fresh holdout human-required | 6/6 retained |
| Development technical unknowns | 4/4 redirected to read-only inspection |
| Fresh holdout technical unknowns | 2/2 redirected to read-only inspection |
| Known-invalid option set | 1/1 redirected to repair |

All 19 synthesized options matched original labels. All 27 human-required questions
remained human questions. On the original 23 hook fixtures, routine automation rose
from 4/8 in iteration 2 to 7/8, with 12/12 human-required questions retained and 2/2
technical unknowns redirected. The latter improvement partly reflects the changed
cost policy: the original technical cases had winning investigate probabilities
.89 and .83, below the old .90 gate. Do not describe that as model accuracy improving.

Four unnecessary escalations remain: generic interchangeable implementations,
historical task granularity, revoked personal-answer mode, and the new three-way
helper-name tie. They remain failures in the denominator. No expectations changed.

One independent judgment was wrong: `limits-five-options` rated option_1 (Python)
acceptable at .94 despite the JavaScript-only requirement. The joint Choice assigned
Python zero probability and selected JavaScript at .96, so the final answer was
correct. This is a real limitation of the model's requirement/reference handling,
not an API impossibility or proof the combined system is safe. The benchmark's
behavior gate passes, but this finding prevents claiming universally reliable checks.

### Live host and deterministic verification

Two real event-hook trials used actual thread history through the CLI fallback:
the routine evidence-preservation question synthesized the correct answer with
`userAnswered: false`; the publishing-permission question retained the inert human
fallback, with approval probability 1.00. The second request contained 34,990
serialized characters. No real human dialog or external action occurred. These
trials verify host event synthesis and fallback, not actual dialog answer delivery.

`bun run typecheck` passes. `bun test`: **17 pass, 0 fail, 237 assertions**. Existing
tests now also distinguish acceptable ties from probability mass on an unsuitable
option, permission uncertainty from safe advice, and the .50 inspection boundary
from the .90 synthesis boundary. Saved-response replay reproduced all 57 final
outcomes and selected indexes with zero inference. The unchanged history guard
tests still cover pagination, compaction, context failure and export metadata.

There were **91 native calls**: 4 first-design, 24 joint-choice development,
4 binary-permission-guard development, 57 final-candidate synthetic, and 2 actual
event trials. All captured model responses were `jev-1.13.0`; no provider failures
or unchanged-revision rerolls occurred. Final synthetic latency: median 143ms,
range 110–268ms, n=57, excluding history retrieval. All 89 synthetic responses,
including the failed handoff case, are preserved in
[compact response evidence](iteration-3-results.json). Private thread text is not.

### Delivery and limits

Changes and evals remain local and uncommitted; nothing was pushed or installed
globally. Temporary evaluation tools are removed after the run. README documents
native full-history fallback, excluded tool evidence, context caps, model-version
routing, unnecessary escalation, imperfect judgments, and untested real-dialog UI.

This meets the small provisional benchmark, not a statistical reliability guarantee
or independent production certification. The fresh holdout is now observed. Future
model/implementation changes require fresh cases and must retain these results.
The explicit `jev_evaluate` comparison path was unchanged and was not rerun live
in this iteration; its deterministic tests pass. No direct provider transport was used.
